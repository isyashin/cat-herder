# Изоляция и границы защиты

## Что нужно обеспечить

Ошибочный исполнитель не должен записать в основной репозиторий, соседний проект, файлы координатора или хранилище ключей. Ограничение проверяется реальными правами, а не фразой в prompt. Отдельный Git clone защищает историю от случайного смешивания, но не запрещает запись по абсолютному пути.

Для строгой границы нужен отдельный пользователь ОС, контейнер или иной sandbox с проверенными mount/ACL и ограниченными секретами/сетью. Такой переносимый контур в Cat Herder пока относится к roadmap. В пилотах Docker не использовался; контейнерный уровень не считается проверенным.

## Что делает исторический Windows-пример

[Текст скрипта](../reference/windows/run-opencode-batch.ps1.txt) создаёт временный deny на запись для текущего SID, проверяет его пробной записью, запускает процессы в отдельных клонах и снимает deny в finally. Логи записываются по мере появления строк, процессы ограничиваются по времени.

Это барьер от случайных записей в защищённые каталоги, а не sandbox для враждебного кода:

- Процесс работает от того же пользователя; владелец с достаточными правами может менять ACL.
- Файлы и секреты вне защищённого набора остаются отдельным риском.
- Принудительное завершение хоста может не выполнить finally.
- Удаление deny текущего SID может затронуть ранее существовавшие deny ACE. Нужны снимок ACL, точное восстановление и испытание этого случая.
- Два независимых запуска могут снять защиту друг у друга; необходим общий lock.
- Текстовые проверки префиксов путей не закрывают junction/symlink/reparse-point обходы.
- Временный deny может мешать и координатору читать/запускать инструменты внутри основного repo. Нужен независимый runtime для проверок.

Поэтому пример сохранён с расширением `.txt` и заменёнными локальными путями. Для исполнения требуется отдельная доработка и проверка на временных репозиториях; он не устанавливает защиту автоматически.

## Проверки для будущего runner

1. Работа только в разрешённом clone, включая разрешение реальных путей/reparse points.
2. Запрет записи в main, соседние проекты, `.git`, инструкции и секреты.
3. Точное восстановление исходных прав при успехе, ошибке старта, тайм-ауте и прерывании.
4. Отказ второго запуска под общим lock.
5. Отсутствие у исполнителя права снять свою изоляцию.
6. Независимая проверка diff и управляемое применение изменений координатором.

Разрешения инструментов OpenCode полезны как дополнительный слой. Они не заменяют границу ОС: [официальные permissions](https://dev.opencode.ai/v2/docs/permissions/).
