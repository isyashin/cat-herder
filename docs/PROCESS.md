# Процесс разработки

Срез методики: 23.10.2026. Для конкретного приложения контракт и проверки находятся в его собственном репозитории.

## Роли и папки

Пользователь задаёт цель и приоритеты. Техдир выбирает архитектуру, делит работу, назначает модель, проверяет результат и принимает интеграцию. Исполнитель OpenCode меняет только разрешённые файлы. Проверки выполняются независимо от его отчёта.

```text
workspace/
  cat-herder/              # Git методики и будущего оркестратора
  app-one/                 # отдельный Git приложения
  app-two/                 # отдельный Git приложения
  .agent-work/TASK-001/    # отдельная копия исполнителя
  .agent-runtime/          # локальные prompts, manifests и логи
```

Ключи и настройки провайдеров остаются вне публичного Git. Расположение каталога не ограничивает права процесса: [изоляция](ISOLATION.md) готовится отдельно.

## Один рабочий цикл

1. **Зафиксировать исходное состояние.** Проверить Git status, сохранить base SHA, цель и очередь.
2. **Определить маленький контракт.** Разрешённые пути, публичные интерфейсы, инварианты, критерии приёмки, команды проверок, бюджет времени и попыток. [Шаблон](../templates/TASK.md).
3. **Выбрать маршрут.** По похожим принятым задачам и текущей доступности; [матрица](MODELS.md) и [дневник](MODEL_JOURNAL.md). Не запускать прогрев ради ответа READY, если доступность можно проверить полезным малым заданием.
4. **Подготовить исполнителя.** Отдельная копия, минимальные инструменты и реальное ограничение доступа к основному проекту. Проверить запрет записи до запуска. Секреты не помещать в prompt.
5. **Запустить и наблюдать.** Смотреть вызовы инструментов, сохранение файлов, ошибки доступа, отсутствие прогресса и лимиты. У каждой задачи свой stdout/stderr и тайм-аут.
6. **Проверить независимо.** Diff, границы файлов, синтаксис, содержательные тесты, настоящее поведение. Для графики — покадровые метрики и просмотр записи, а не только статический PNG.
7. **Интегрировать принятый результат.** Перенести проверенные изменения в основной Git, повторить нужные проверки и создать commit. Непринятый diff остаётся в копии исполнителя.
8. **Записать опыт.** Модель/маршрут, доступность, качество, повторы, время и расход. [Шаблон оценки](../templates/MODEL_REVIEW.md).

## Когда исполнитель ошибся

Одна содержательная коррекция с новым фактом: конкретный тест, ошибка API или недостающее требование. Если тот же критерий снова сорван, сменить маршрут либо уменьшить задачу. При `429` не устраивать цикл повторов; учитывать общий лимит провайдера, даже если процессов несколько.

Сохранять [передачу состояния](../templates/HANDOFF.md): принятое, текущий diff, ошибка и следующий проверяемый шаг. Полная история неудачной сессии новому агенту обычно не нужна.

## Параллельная работа

Параллелить независимые файлы/модули и пробы. У каждого исполнителя отдельная копия, base SHA и договорённый интерфейс. Квота провайдера важнее числа ядер. Один общий цикл защиты основного workspace; два независимо снимающих ACL процесса могут разрушить эту защиту.

## Уроки пилотов

- `exit 0` встречался без единого записанного файла; полезный diff сохранялся до последующего отказа квоты с ненулевым exit.
- Математически согласованный меш оказался несовместим с системой координат движка. Регрессия теперь сверяется со штатным примитивом и проверяет пиксели пола.
- Снимки через чётное число кадров скрывали поворот камеры на 180° каждый кадр. Ориентацию нужно было измерять покадрово.
- Узкий JSON-патч полезен для точной замены, но требует проверки пути, кратности совпадений и настоящего запуска.
